# 撮影 → 半自動アノテーション → YOLO学習

> 現行のレビュー手順と追加仕様: [レビューUI改善仕様](review_ui_improvements.md)と[YOLO部分公開契約](contracts/yolo_publication.md)を参照。YOLO一括確認・候補に応じた保存、DINOタグ単位の部分保存、2026-11-13合意の一括確認APIは実装・自動テスト済みで、手動確認待ち。公開済み変更版の扱いは保留中。
>
> SAM3へのYOLO bbox入力を追加する場合は[合意済み仕様](sam3_yolo_bbox_inference.md)を参照する。公開契約はSAM3推論結果だけを公開対象とする既存範囲を維持し、追加の契約変更は不要。

## 対象と前提

- `shared_data/YYYY-MM-DD/<session_id>/metadata.sqlite3` とRGB原本を入力とする。全セッションDBを日付・セッションのパス順に探索し、読み取り専用で開く。
- 撮影APIはセッションごとにDBを作成する。SAM3の入力は各セッションの撮影・タグ表を正本とし、ルート直下の旧`metadata.sqlite3`は読み込まない。旧DBへのフォールバック・移行・削除は行わない。
- 撮影・推論原本・レビュー・承認台帳・公開状態は、すべて所属セッションDBを正本とする。SAM3の通常CLIはルート直下の旧単一DBを必要としない。今回の対応はSAM3側の保存までであり、DINOv3・YOLO側のセッション横断読み取りと日次レポートJSONの形式は変更しない。
- `tag_status=tagged` の画像だけを取り込む。撮影直後の未タグ画像は推論対象にしない。
- SAM3には全画像で同じテキストプロンプトを使う。器具名別推論やタグ点を入力した追加推論は行わない。YOLO bbox入力の有効化と、正常なYOLO検出0件時のテキスト単独推論へのフォールバックは[YOLO bbox入力仕様](sam3_yolo_bbox_inference.md)に従う。
- タグは推論後の「マスク候補 → 器具UID」の対応付けに使用する。共通プロンプトによる全器具の検出は保証されない。
- 最初の対象タスクはYOLOの矩形物体検出。polygon・point形状を学習用矩形として誤変換しない。
- Python 3.12を使う。YOLO bboxをSAM3推論で使う場合は、SAM3実行環境に`ultralytics`をインストールする。YOLOの学習環境は引き続き分離する。

## 設定

`sam3_project/src/configs/capture.json` のパスは設定ファイルの場所を基準とする。

| 項目 | 用途 |
|---|---|
| `capture_root` | 撮影APIの `IC_DATA_DIR`。画像の `images.path` はこのルート基準 |
| `targets` | 任意。`date`必須、`session_id`任意の日付・セッション対象条件。複数条件はORで、同じDBは一度だけ処理する。指定時は入力・現行性確認・レビュー/推論の保存先を対象DBに限定する |
| `output_root` | 撮影データと分離したアノテーション作業領域 |
| `mask_root` | `capture_root`内の物体別mask PNG保存先。省略時は`capture_root/annotations/sam3` |
| `checkpoint` | 任意のローカルSAM3重み。`null` の場合はSAM3モデルビルダーがHugging Faceから取得する |
| `bpe_path` | 明示指定しない場合はインストール済みSAM3の語彙ファイル |
| `prompt` | 全画像共通のテキスト。初期値は `surgical instrument` |
| `min_score` | SAM3 processorと出力候補に適用する閾値 |
| `use_yolo` | SAM3推論へ検出bboxを渡すか。初期値は `false`。`true`時だけYOLO推論を実行する |
| `yolo_confidence` | YOLO検出のconfidence閾値。初期値は `0.8`。有効値は `0`以上`1`以下 |
| YOLO重み設定 | `use_yolo=true`時は `src/configs/settings_yolo.yaml` を使用し、指定された重みファイルの内容hashをキャッシュ署名に含める |
| `matching.max_distance` | 中心点からマスクまでの許容距離。画像対角長に対する比率 |
| `matching.ambiguity_margin` | 対応付け候補のコスト差が小さい場合に確定を保留する閾値 |
| `review_confidence.medium_score` | 中信頼度として扱う最低SAM3スコア |
| `review_confidence.high_score` | 高信頼度として扱う最低SAM3スコア。タグ点がbbox内で、対応が曖昧でないことも必要 |

各セッションSQLiteの`tagged`行と`images.path`がアノテーション対象を決める。`capture_root`にはDBファイルやセッションディレクトリではなく、共有データルートを指定する。画像パスも引き続きこのルートを基準に解決する。レビュー画面は起動時点の対象集合に固定し、後から追加された画像は次回起動で取り込む。別PCのデータを使う場合も、そのPCの`IC_DATA_DIR`を本設定の`capture_root`に指定する。

`targets`を設定すると、推論・選択一覧・SQL上の現行性確認はその範囲のセッションDBだけを参照する。各条件は`{"date":"YYYY-MM-DD"}`または`{"date":"YYYY-MM-DD","session_id":"session_001"}`で、条件の組み合わせはORである。日付は実在する日付、セッションIDは英数字で始まる英数字・`.`・`_`・`-`の80文字以内に限る。条件の一部でも対応DBがない場合や、`targets`が空・不正な場合はエラーとして停止する。`targets`キーを省略した場合だけ従来どおり全セッションDBを対象とする。

`capture.json`では、次のように`targets`を追加する。

```json
{
  "capture_root": "../../../shared_data/",
  "output_root": "../../../annotation_work",
  "targets": [
    {
      "date": "2026-11-24"
    },
    {
      "date": "2026-11-25",
      "session_id": "session_001"
    }
  ]
}
```

この例では、`2026-11-24`の全セッションと、`2026-11-25`の`session_001`だけが対象になる。特定セッションだけに絞る場合は、`date`と`session_id`を指定する。日付ごとの全セッションを対象にする場合は、`session_id`を省略する。`targets`には実際に使う他の設定項目（`mask_root`、モデル設定、`matching`、`review_confidence`など）もそのまま含める。

個別画像の再取得と現行性確認も所属セッションDBを参照する。タグ版が変われば古い入力は現行と扱わず、画像行・DB・画像原本の削除、未タグ化も検出する。セッションDBが一つもない場合、DB破損・スキーマ不整合・画像の不正やハッシュ不一致はエラーとし、不正DBや不正画像では対象DBを明示して処理を停止する。異常なセッションを黙って除外して続行しない。

以下は従来のYOLO側の構成であり、セッションDB対応は別タスクである。現状の単一DB台帳をそのまま今回の出力へ接続することはできない。`yolo_train/src/capture_training.json` も設定ファイル基準でパスを解決する。

- `capture_root`: 撮影APIの `IC_DATA_DIR`。データセット作成・検証・学習開始ごとに、入力画像が現在も `tagged` としてSQLに存在することを照合する。
- `dataset_root`: バージョン別データセットの親ディレクトリ。
- 器具UID→クラスID、セッション→split、画像採用、run履歴は`capture_root/metadata.sqlite3`へ保存する。
- `initial_weights`: ローカルYOLO初期重み。既定は既存の `yolo_train/yolov12n.pt`。
- `training_root`: 学習実験の親ディレクトリ。
- `training`: エポック数、バッチ数、画像サイズ、計算デバイス、乱数シード。
- `split`: 初回データセットのtrain/val/test比率と決定的タイブレーク設定。初回割当後の既存セッションは移動しない。

初回は対象manifestの全画像数をセッションごとに集計し、セッションを分割せずに目標比へ近づける。別セッションのtrainとvalを構成できない場合はdatasetの公開を拒否する。最初の検証dataset公開後、新しいセッションはtrainへ追加し、初回に固定したval/test画像とラベルは以後のdataset版へコピーする。

依存宣言は更新済み。初回は各プロジェクトで `uv sync` を実行する。
モデルパッケージ・GPU・ドライバの対応は各環境で確認する。HF取得を使う場合はモデルへのアクセス権と `src/.env` の `HF_TOKEN` を確認する。ローカル重みを指定した場合はダウンロードしない。

## 1. 推論と一括レビュー

プロジェクトルートから実行する。推論完了後、ブラウザーでローカルレビュー画面が開く。

```powershell
uv run python src/capture_workflow.py run --limit 5
```

動作確認後、`--limit 5` を外すと全件を処理する。途中終了後に既存草案だけを開く場合は `uv run python src/capture_workflow.py review` を実行する。独自設定は `--config <設定JSON>` をサブコマンドより前に指定する。

現在のrunフローでは、画像選択後にselection serverが終了し、レビューserverが別に起動する。レビュー画面で「作業完了」を押したときは既存の画像選択画面`selection.html`へ戻る。完了はユーザーの明示操作を指し、DINO保存やYOLO公開を意味せず、それらを暗黙に実行しない。選択画面・レビュー画面とも既存HTMLを使い、新しいHTMLページは作らない。

画面上部で撮影セッションを選択すると、そのセッションの画像だけが一覧に表示される。セッションIDはSQLの `session_id` を使用し、撮影データの保存フォルダーとも対応する。実画像の上にSAM3矩形とSQLiteタグ点を重ね、信頼度フィルターで「低・中・高・未確認」を切り替える。低信頼度やタグ不一致だけ詳細を開いて矩形を追加・削除・再ラベルできる。公開したい画像を確認し、各画像の「YOLO確認済み」をチェックする。

一覧画面には、選択中のセッション全体の未確認画像を一括でYOLO確認済みにする操作がある。操作時にUIは`POST /api/reviewed/batch`へ`session_id`を送り、サーバーが指定セッション内の現行・最新レビュー画像から対象を判定する。対象は未確認で、保存済み注釈に採用bboxが1件以上ある画像に限る。bboxが0件の画像は対象外であり、ページ・信頼度・UIフィルターには依存しない。既存の画像単位`POST /api/reviewed`は維持され、詳細画面からの確認に使う。既存の「高信頼度を一括YOLO確認済みにする」は別の操作として維持する。一括操作はYOLO確認状態だけを変更し、候補の採否・注釈・DINO状態・承認・公開状態は変更せず、`allow_empty`と`exception_note`を保持する。一部失敗時は成功分だけ確認済みとし、失敗件数と画像別エラーを通知する。採用bboxがない画像は注釈を保存せず、人手でbboxを修正した画像は候補がなくても保存できる。bboxが0件の負例を保存する必要はない。

信頼度は `review_confidence` とタグ情報から分類する。

| 分類 | 基準 | 確認の目安 |
|---|---|---|
| 高 | スコアが `high_score` 以上、利用可能なタグ点がすべてbbox内、対応に未解決事項がない | 一覧で軽く確認 |
| 中 | スコアが `medium_score` 以上で中心点がbbox内だが、高の条件を満たさない | 通常確認 |
| 低 | 低スコア、bbox外タグ点、未対応・曖昧な対応、検出なしなど | 詳細画像を確認・修正 |

信頼度は確認の優先度であり、自動承認ではない。スコア閾値はデータで適合性を確認して調整する。

処理内容:

1. セッションごとにSQLiteの読み取りトランザクションを作り、画像・宣言・タグのスナップショットを取得する。
2. 画像ハッシュを検証し、SAM3のbbox・score・モデル署名を所属セッションSQLへ、候補maskを物体別PNGへ保存する。SQL未登録なら同じキーの旧NPZを取り込む。
3. 正規化された中心点とマスクの距離、可視端点の距離を使い、SciPyの線形割当で一対一対応付けする。
4. 一意に対応した候補だけをタグ対応付きの学習用`shapes`へ入れ、未解決候補は未解決ラベルのまま`review_candidates`へ分けて、画像ごとに1つのLabelme JSONを作る。bbox・score・group_id・descriptionはどちらも保持し、未解決候補へ自動でラベルを付けない。初期保存からこの形式を使うため、対応済みbboxは「修正を保存」前でも確認・公開できる。旧形式の注釈は従来どおり読み込みできる。初期生成物と内容が完全一致し、未確認・未承認の旧草案だけは起動時に安全に移行する。編集済み・確認済み・承認済みの注釈は自動移行しない。

推定中心点は弱い証拠として扱い、レビュー事項に記録する。画面外タグと点なしタグは位置対応に使用しない。
点なしで存在だけ記録された可視タグは、確認事項として残す。
中心点が器具の穴の背景上にある場合も扱えるよう、厳密なマスク包含だけで判定しない。
遮蔽部の形状を推測して補完する処理はない。bboxの可視範囲・遮蔽時のラベル方針はレビューで統一する。

```text
annotation_work/
  cache/<prediction_key>.npz         # 旧キャッシュ。通常CLIの新規推論では作成しない
  drafts/<revision>/metadata.json   # 元タグ、器具名スナップショット、未解決事項
  reviews/<revision>/annotation.json # SQL相対パスを参照するレビュー注釈
  latest/<image_identity>.json      # 現在の入力に対応するリビジョン
  approvals/<revision>.json        # 明示承認の記録
  approved/                         # 旧形式の履歴のみ。新規承認では画像コピーを作らない
  review_progress.json              # 一覧確認・例外理由・空画像確認
  exports/<session_id>/manifest.json # セッション単位のYOLO互換公開バッチ
```

キャッシュは画像・重み・プロンプト・閾値・実装識別情報から決定する。
タグ更新や対応付け設定だけの変更ではモデル候補を再利用する。
YOLOを使う場合は利用有無・confidence・`settings_yolo.yaml`から解決した重みファイル内容hashも署名に含めるため、YOLOあり／なしや異なるYOLO重みのキャッシュを混同しない。YOLO推論が正常終了して検出0件ならテキスト単独推論へ進むが、YOLO推論自体の失敗は明示的な失敗とし、SAM3単独推論へ切り替えない。詳細は[YOLO bbox入力仕様](sam3_yolo_bbox_inference.md)を参照。
再実行は同じレビューJSONを上書きしない。タグが更新されると別リビジョンができ、旧承認の新規出力を拒否する。

### 推論原本のSQL・PNG保存と移行

通常CLIは推論情報をSQLへ記録し、確認用maskはメモリー上で保持する。正式PNGは画像承認時だけ保存する。レビューJSON、承認JSON、YOLO互換exportは従来どおりであり、旧ディレクトリは自動削除しない。`annotate`／`annotate_samples`を直接呼び出す場合、`prediction_store`を省略すると従来のNPZ経路を使う。

| SQLテーブル | 所有者と役割 |
|---|---|
| `sam3_schema_migrations` | SAM3が所有する追加schemaの適用版。現行は1。未対応版は拒否する |
| `sam3_predictions` | 画像・推論ID・原本hash・寸法・モデル署名・設定情報・由来・物体数。0件も含めた完了結果 |
| `sam3_prediction_objects` | 物体番号・推論bbox・score・mask識別子とhash。新規の未承認maskはファイルパスではなく`memory:`識別子であり、PNGは存在しない。1物体1行 |

物体の主キーは`(session_id, image_id, prediction_id, object_index)`である。推論IDは既存と同じ画像hash・推論署名から作り、タグ変更では変わらない。番号は候補番号を維持し、最小3桁で出力する。欠番を詰めず、1000以上でも切り詰めない。

```text
shared_data/
  YYYY-MM-DD/<session_id>/
    metadata.sqlite3
    masks/                 # 画像承認時に初めて生成する
      <画像名>_000.png
      <画像名>_001.png
```

正式保存するmaskは元RGBと同寸法の8bitグレースケールPNGで、背景0／物体255である。元画像・maskのhash、寸法、bbox範囲、score、番号の一意性を検証する。承認前にPNGがないことは正常である。旧PNGが欠損していても一覧は表示でき、確認時に同じ設定でSAM3を再実行する。存在する保存済みPNGのhash改変はエラーにする。

推論情報のSQL記録だけではmaskを正式保存・公開しない。プロセス終了で確認用maskは失われるため、再開時は保存済みmaskを検証して読むか、表示時にSAM3を再推論する。既存SQLに対して再推論のbbox・score・mask hashが異なる場合は、旧承認を流用せずエラーにする。その場合は設定を更新して`run`で新しいレビュー版を生成する。SQLiteロック待ちは`sqlite_timeout`で制限する。

旧NPZ成果物の一括移行は、書き込み処理を停止し、各セッションDBと`annotation_work`をバックアップした後に行う。ルート直下の旧単一DBからの移行は行わない。

```powershell
uv run python src/capture_workflow.py migrate-predictions
```

- 草案の`metadata.json`にある`prediction_key`と撮影画像参照を使う。草案から参照されない孤立NPZは、画像との対応を推測せず残す。
- 現行SQLから同じパスで取得でき、元画像hash・寸法が一致するものを移行する。削除済み・原本変更済みは対象外とする。タグ版だけの違いは推論原本の再利用を妨げない。
- 同一画像・同一推論を重複排除し、再実行でも重複登録しない。ログの処理件数には移行済みの照合も含む。
- 参照先NPZが欠損・不正な場合はエラーにする。既に保存済みの結果は消さず、修復後の再実行で続行できる。
- 旧NPZからモデル署名を復元できないため、`model_signature=NULL`、`model_metadata_json={}`、`provenance=legacy_npz`として保持する。新規推論は`provenance=native`で署名と非機密のモデル設定を保存する。
- 元NPZ、レビュー、承認、YOLO exportを変更・削除しない。移行によってDINO採用済みとは扱わない。

このコマンドはモデルやGPUを初期化せず、PNGも出力しない。通常起動では旧NPZを一括移行せず、現行レビュー情報だけを同期する。`run`では必要な画像の旧NPZがあれば取り込める。運用データでの初回実行前には必ずバックアップする。DINO側のセッションDBへの入力接続は今回の変更範囲外である。

### 物体別DINO確認

一覧では撮影元パスの上位フォルダーに基づく「撮影日」を先に選び、その日付のセッションを選択する。日付は新しい順に表示し、画像カードと詳細タイトルにも表示する。日付を変更すると選択可能なセッションを絞り込み、一括公開の対象選択チェックを解除する。選択候補はレビュー可能な草案がある日付・セッションのみである。`GET /api/items`の画像情報に`capture_date`を追加し、既存のセッションIDと公開先は変更しない。

元bbox・maskを物体ごとに確認し、画像単位で一括保存する。既存草案は`uv run python src/capture_workflow.py review`で確認できる。旧bbox承認を取り込んだ場合も、物体採否は未判定から始まる。

開始画面の画像カードは、信頼度とモデル別承認状況を別々に表示する。信頼度は「低・中・高」の文字と1〜3本のメーターで示し、承認状態には青いチェック付きラベルを用いる。YOLOは画像承認の有無、DINOは画像承認に加えて全物体の判定完了と1件以上の採用が揃った場合に「承認済」と表示する。DINOには採用・不採用・未判定の件数も表示し、「未判定」「判定途中」「未承認」「判定済（採用なし）」「対象なし」を区別する。DINOの状態表示は永続化された判定・承認状態に基づき、maskファイルの存在だけを判定済みの根拠にしない。maskの存在情報は上書き確認用であり、承認表示はレビュー状態であって取得時のmaskファイル整合性検証を代替しない。一覧確認済みや高信頼度だけでは承認済みにせず、YOLO用の一括公開状態とも区別する。DINO状態はYOLO状態から独立し、DINOの一覧判定はYOLO状態を変更しない。

1. 画面上部に確認担当者を一度入力し、一覧の「DINO物体確認」を開く。詳細画面の「YOLO注釈」と「DINO原本確認」は別モードである。
2. 物体番号を選択し、元RGBに重ねた推論bbox・maskを確認する。DINO側では矩形編集もmask補正もできない。
3. タグごとに採用候補を1つ選ぶ。採用した候補と同じタグの残りは自動で不採用になり、他タグの候補は独立して扱う。保存前の選択は画面内で保持する。
4. 画像全体を確認し「保存して次へ」を実行する。採用候補が1件以上ある場合、採用候補と画像承認を同一SQLトランザクションで確定し、同じセッションの次画像を開く。採用候補のmask確認は必要だが、他候補の個別確認は不要である。採用候補が0件なら保存せず、現在の画像に留まる。未保存のYOLO矩形変更がある場合も進めない。タグ数との相違は既存の例外理由が必要であり、空画像は一覧で真の負例として明示確認する。

詳細画面の担当者欄、物体ごとの保存ボタン、画像承認のチェックとボタンは廃止した。変更して閉じる際は「変更を破棄して閉じる／確認を続ける」を表示し、Escapeと背景クリックにも適用する。ページ離脱時も未保存変更を警告する。未保存変更がある間はモードを切り替えず、現在のモードで保存するか破棄してから移る。DINOで「使わない」にしてもYOLO矩形は削除せず、YOLO一括公開も実行しない。

APIは`POST /api/complete-review`を追加した。`revision`、`reviewer`、`confirm_complete: true`、今回確定する物体の`decisions: [{object_index, status}]`（`accepted`または`rejected`）を渡す。未指定の候補は既存状態を維持する。既存の物体単位保存・画像承認APIは互換性のため維持する。保存ポートの`record_annotation`と`FileAnnotationStore.approve`には省略可能な一括判定・上書き同意引数を追加した。

#### 承認用maskと上書き確認

以下は[DINO mask保存バグ修正仕様](dino_mask_save_fix.md)に合わせた実装済みの動作である（手動確認待ち）。タグ単位の部分保存は[レビューUI改善仕様](review_ui_improvements.md)と[公開参照の契約](contracts/dino_mask_publication.md)を参照する。

「保存して次へ」で、今回採用した推論maskだけを`日付/<session_id>/masks/<画像名>_<物体番号>.png`へ正式保存する。不採用候補のPNGは作成せず、判定履歴は保持する。別の「原本PNG」は事前保存しない。複数の採用物体はそれぞれ別PNGであり、推論IDのフォルダーは付けない。YOLO矩形からmaskを再生成する処理ではない。採用候補が1件以上あれば、同じタグの残り候補を自動で不採用として保存する。採用候補が0件なら保存しない。

GUIは物体ごとに「保存済みmaskあり／なし」を表示する。保存直前に存在情報を再取得し、UIの未保存の今回採否が採用である候補を、最新の同じ候補indexの存在情報と照合する。採用先に既存ファイルがあるときだけ「Yes（上書きして保存）／No（保存せず戻る）」を表示する。不採用先だけにファイルがある場合は確認しない。NoまたはEscapeでは採否・承認・ファイルを変更せず同じ画像に留まる。APIも同じ採用対象に対して`overwrite_masks: true`の明示同意を検証する。

再保存の成功時に旧採用maskを削除し、今回採用したmaskだけを残す。既存バグ由来の不採用maskも、採用候補がある対象画像の保存時に整理する。採用候補が0件なら保存・整理を行わない。安全に画像所有を識別できる承認用maskだけを対象とし、他画像・他セッション・推論原本・監査履歴は削除しない。所有は全レビュー版の承認mask台帳と画像キーで確定し、旧版の正式参照を外して推論参照へ戻す。候補保存先に台帳未登録の既存ファイルがある場合や原本共有は、推測で変更せず保存を停止する。詳細は[修正仕様の実装決定事項](dino_mask_save_fix.md#実装決定事項)を参照する。

既存の`sam3_approved_masks`（レビュー版・物体番号・正式maskの相対パス・hash）とDINO公開参照を保存・整理結果に整合させ、削除済みPNGを有効な現行参照にしない。採否・対応・承認の監査履歴は保持するが、当時のパスの現存は保証しない。新規の`memory:`識別子は公開条件を満たさない。`GET /api/items`の`saved_mask_exists`は正式保存先の実ファイル有無を示す。`mask_root`は旧設定互換用であり、そこへの新規PNG出力・一括移行は行わない。本修正による整理は対象画像の承認用maskに限定する。

PNG作成・置換・不要mask削除と、採否・対応・画像承認・台帳・公開参照を保存成功時だけ確定する。通常の保存失敗およびSQL確定失敗時は削除分も含めファイルとDB状態を変更前へ維持／復元する。ファイルシステムとSQLiteをまたぐクラッシュ原子性は従来どおり保証しないため、取得側はhashを検証する。別画像が同じファイル名を使用している場合は、上書き同意があっても拒否する。YOLO矩形・YOLO承認状態は変更しない。

「高信頼度を一括確認済みにする」は画像一覧の確認であり、物体別DINO採用にはしない。器具対応未確定の物体は採用を拒否する。担当者・原本確認・現行版・maskの整合性はAPIでも検証する。

| SQLテーブル／ビュー | 内容 |
|---|---|
| `sam3_review_schema_migrations` | レビュー専用schemaの適用版。推論schemaとは独立して管理し、現行は5。本mask保存修正での版追加は未決定 |
| `sam3_review_revisions` | 推論・タグ・レビュー版、現行版フラグ、YOLO用注釈、一覧確認状態、画像承認のSQLスナップショット |
| `sam3_object_reviews` | レビュー版・固定物体番号ごとの器具対応、採否、担当者、確認日時 |
| `sam3_object_review_events` | 採否変更と取消による未確認化の履歴 |
| `sam3_approved_masks` | 画像単位の保存・不要mask整理と整合する承認用maskのパスとhash。監査履歴とは区別する |
| `sam3_review_events` | YOLO用注釈と画像承認・取消の履歴 |
| `sam3_dino_objects` | 有効な画像承認と物体別採用が揃った推論原本だけを返す公開ビュー |

公開ビューは現行レビュー版、画像承認、`accepted`、器具対応を要求する。さらに撮影SQLのtagged状態・タグ版・原本hash・パス・寸法を照合する。maskファイルの存在・hash検証はビューだけでは行えないため、今回の確認APIでも、後続のDINO取得側でも検証する。

3物体中`000`と`002`だけを採用した場合、正式PNGと公開行はこの2物体だけとなる。`001`の候補・判定履歴は削除せず、番号も詰めないが、対象画像の不要な承認用PNGは保存成功時に整理する。YOLO用bboxを編集してもDINO推論原本のbbox・maskは不変であり、別物体の修正を理由に確認済み物体を自動除外しない。編集後は画像承認を無効にして再承認を要求する。

画像承認を取り消すと物体採否も未確認へ戻す。再承認だけでは以前の採用は復活しない。新しいレビュー版にも旧判定を引き継がない。旧版・取消・不採用・未確認は新規公開の対象外となる。

一覧確認状態と物体採否はSQLから復元する。YOLO用レビュー・承認はSQLへ同期しつつ、従来のJSONファイルとmanifestも維持する。SQLへ登録済みの取消や注釈変更を、残存JSONの承認で復活させない。既存ディレクトリの削除とYOLO exportのファイル依存の解消は今回の対象外である。DINO側には単一DBの公開ビューを読む実装があるが、各セッションDBを横断する対応は別途必要である。

### DINO・YOLO専用の結果テーブル

各セッションDBに次のテーブルを追加する。呼び出し側から編集する正本ではなく、同じDBの推論・レビュー・承認台帳から同一トランザクションで生成・更新する公開スナップショットである。

| テーブル | 単位 | 保存する主な情報 |
|---|---|---|
| `sam3_dino_results` | `(revision, object_index)` | セッション・画像・推論ID、タグ版、原画像・depth参照、hash・寸法、`prompt`・`min_score`・モデル署名と設定、`sam3_score`、元座標系のxyxy bbox、maskパス・hash、器具UID・個体番号、採否・担当者・確認日時・イベントID、画像承認ID、`is_dino_ready` |
| `sam3_yolo_results` | `revision` | セッション・画像ID、タグ版、原画像スナップショット、編集済み注釈JSON・hash・作業領域相対パス、承認JSON・ID・担当者・日時、空画像確認・例外理由、manifestパス・公開日時、`is_yolo_ready` |

- 初期状態では両フラグとも0である。物体が0件ならDINO行はなく、推論完了行とYOLO画像行は保持する。
- `is_dino_ready=1`は現行版・有効な画像承認・物体別`accepted`・器具対応・撮影タグ版と原本情報の一致を要求する。採用だけ、または画像承認だけでは公開しない。
- `is_yolo_ready=1`は現行承認と注釈hashに一致したmanifestの公開完了を要求する。画像承認だけでは公開しない。従来のschema version 1のmanifestとLabelme JSONを維持する。
- 両フラグは独立する。DINO採否の変更はYOLO公開を変更せず、YOLO用bboxの編集はDINO原本のbbox・maskを変更しない。ただし画像承認を失効させるため、編集後は画像の再承認が必要である。
- 取消・新レビュー版は旧版のフラグを失効させる。取消後の物体採否は未確認となり、再承認だけで復活しない。撮影行のタグ版・tagged状態・原画像hash・パス・寸法・識別子の変更と削除はSQLトリガーで即時に両フラグを0へ戻す。
- フラグは「下流へ渡せる状態」であり、DINOv3・YOLOの処理済み情報ではない。ファイルの削除・改変はSQLだけでは検出できないため、取得側で原画像・mask・注釈・manifestの存在とhashを再検証する。
- maskは従来の`mask_root`へ保存し、パスは共有ルート相対である。DBの保存先変更によってmaskや原画像を複製・移動しない。旧NPZで復元できないpromptや閾値はNULLとし、推測しない。
- 既存の`sam3_predictions`・`sam3_prediction_objects`・レビュー履歴・`annotation_revisions`・`sam3_dino_objects`ビューも各セッション内で維持する。ルート直下の旧単一DBは参照・生成・移行しない。

## 2. 一括承認と公開

### タグ別のYOLO確認と手描き

「YOLO注釈」は確認モードを初期表示する。器具UID＋個体番号ごとにタグを選び、同色・同番号のタグ点とbboxを確認する。bboxをクリックすると対応タグが右側で選択される。未対応候補では対応先が未確定であることを表示し、選択タグへ採用する。重なったbboxは再クリックで巡回し、bbox一覧からも選択できる。「前のタグ」「次のタグ」で物体単位に移動できる。信頼度は色ではなくスコア表示と一覧の既存メーターで確認する。

使える候補がない場合は、対象タグを選んで描画モードへ切り替え、画像上をドラッグする。手描きbboxは選択タグへ採用され、確認モードへ戻る。既存の採用bboxの置換は明示確認を要求し、解除された矩形は比較用候補へ戻す。短すぎるドラッグは矩形にしない。確認モードのクリックでは描画しない。

新形式は`tag_review_version=1`とし、採用矩形だけを`shapes`に保存する。各採用矩形の`tag_assignment`へ`instrument_uid`と`instance_no`を記録し、1タグ・1bboxの対応を保存時と承認時に検証する。未採用候補は`review_candidates`へ保存し、再起動後も比較できるが学習用矩形には含めない。候補をすべて不採用にした結果bboxが0件の場合、このレビューUIでは注釈を保存せず、負例保存もしない。

旧注釈は変更せず読める。画面では保存済み個体番号、または同UIDの可視タグが一つだけの場合に対応を復元する。個体を特定できない場合は推測せず候補として表示する。新形式への移行は「修正を保存」で行い、以後の旧形式への戻しは拒否する。手描き・対応変更はYOLOだけを変更し、DINOの推論bbox・mask・物体採否は変更しない。画像承認は失効するため、保存後は再承認・再公開が必要である。

### タグ別のDINO候補選択

DINO原本確認にも可視タグの一覧と「前のタグ」「次のタグ」を用意する。器具UID＋個体番号のタグを選び、画像上のbboxまたは候補一覧から推論maskを確認して「選択タグにこのDINO候補を採用」を押す。重なったbboxはクリックで巡回できる。自動対応の曖昧さや低スコアで手動採用を禁止しない。原画像・推論bbox・maskは変更せず、DINOの手動対応と採否だけを編集する。YOLOの手描きbboxはDINO候補へ変換しない。

1タグの採用候補は最大1つである。タグに候補を採用すると、同じタグの残り候補は自動で不採用になる。採用されない他タグの候補はpendingのまま残り、個別確認を求めない。サーバーも可視タグ・個体番号・候補番号・採用重複を検証する。対象タグがない場合は撮影側でタグを修正する。

タグごとの採否は独立して扱うため、他タグの候補を個別に確認しなくても保存できる。画像内に採用マスクが1件以上ある場合に保存でき、採用がないタグはpendingのまま保存対象に含めない。画像内の採用マスクが0件なら保存対象がないため保存しない。

レビューschema version 5は`sam3_object_assignment_events`へ変更前後のUID・個体番号・担当者・時刻を追加記録する。旧schemaは非破壊更新し、既存対応・採否は維持する。手動対応と採否・承認・正式maskの保存は同一処理内で確定し、通常の保存失敗では元へ戻す。ファイルシステムとDBをまたぐクラッシュ原子性は従来どおり保証しない。

`POST /api/complete-review`へ今回確定する候補分の`assignments: [{object_index, instrument_uid, instance_no}]`を指定すると、YOLO注釈が未解決でもDINOを確定できる。未対応はUIDと個体番号をともに`null`にする。有効なYOLO承認がなければDINO専用承認（`scope=dino`）とし、YOLO用承認JSONは生成しない。既に注釈hashの一致する現行YOLO承認・公開があれば、そのID・担当者・公開状態は維持し、DINO担当者と物体判定だけを別に記録する。古いmanifestや失効した承認JSONからDINO専用承認をYOLO承認へ復活させない。従来の`assignments`未指定APIは互換のため従来の画像承認条件を維持する。

レビュー画面でセッションを選択し、担当者名を入力して「YOLO確認済み画像だけを公開する」にチェックした後、「YOLO用に一括公開」を実行する。選択セッション内のYOLO確認済みかつ未公開の画像だけを対象にし、未確認画像は除外する。公開対象と未確認件数を事前表示し、対象が0件なら公開しない。公開先は `exports/<session_id>` または追加分の別フォルダーに自動決定され、フォルダー名の入力は不要である。タグ数と矩形数が異なる場合は、その画像の例外理由を入力する。矩形0件の画像は、真の負例として確認した場合だけ明示チェックする。一括公開の注釈検証エラーは対象画像IDと問題のshape番号・fieldを示し、問題のshapeを特定できるようにする。無効データを黙って除外して公開せず、仕様変更で適正な注釈を誤拒否している場合は原因を修正する。

公開対象チェックは、未確認画像を自動で確認済みにする操作ではない。未確認画像が残っていても、その画像を除外して公開できる。担当者未入力、対象画像0件、公開対象チェック未選択の場合は、それぞれ不足条件を示す。

公開はschema version 1のmanifest、注釈JSON、UID・SHA-256承認記録を生成する。画像は撮影SQLの相対パスで参照し、レビュー領域・承認領域・公開バッチへ複製しない。出力先の再利用は拒否される。レビューJSONが承認後に変更された場合やSQLから対象が削除された場合は、公開を拒否する。

同じ画像の新しいタグ版を再推論した後に古い承認が残っている場合は、古い承認を将来の出力対象から外す。

```powershell
uv run python src/capture_workflow.py revoke <旧revision>
```

過去の成果物は履歴として残るが、現行SQLに存在しないデータは新しい公開から除外される。既に完了した学習履歴は遡及変更しない。公開フラグの失効はSQLトリガーが行う。新しいタグ版に対応したレビュー草案の作成には`annotate`の再実行が必要であり、撮影DBを常時監視して再推論する処理はない。

## 3. YOLOデータセット作成と学習

**この節の学習側設計は従来経路の説明である。** 現在のYOLO側は単一DBの台帳を参照するため、今回のセッション別出力を使うには読み取り側の別途対応が必要である。互換のために旧単一DBを新規作成・再集約する運用は行わない。

SAM3の`status`は、既存の承認manifestを所属セッションの承認台帳へ同期する。

```powershell
# sam3_projectから。既存のannotation_work/exportsを各セッションDBへ同期
uv run python src/capture_workflow.py status
```

既存の `json_to_yolo_ann_2.py` と `convert_labelme_to_yolo.py` は、この新しい撮影データ経路では使用しない。
承認バッチから直接変換し、shapeハッシュの差分を「人手承認」とみなす旧方式も使用しない。

- クラスIDはUIDごとに固定し、新規UIDだけを追記する。既存のクラスIDを並べ替えない。
- 同一セッションの全画像は同じ分割に固定する。連写・同一配置の評価データへの混入を防ぐ。
- 初回は画像数の比率を使ってセッション単位で自動分割し、登録後は変更しない。
- 追加収集分はtrainに加え、初回の固定validation/test画像を変更しない。
- 同一画像ハッシュの重複や分割またぎも拒否する。
- 画像、YOLOラベル、UID対応、承認ID、タグ版、分割を新しいデータセット版へ保存する。
- 学習直前に画像・ラベル・設定を検証し、train/valの独立した非空セッションを要求する。
- 学習は実験ディレクトリ内のデータコピーを使う。Ultralyticsのキャッシュは固定データセットに書き込まない。
- testは学習・通常のvalidationに使用しない。最終評価用として分離して保持する。
- `training_recipe.json` に設定、入力のハッシュ、ランタイム版、成否、validation指標、出力重みのハッシュを記録する。

## 次のサイクル

追加撮影 → タグ確定 → 再度annotate → 修正・承認 → 新バッチ → 新データセット版 → 新学習実験、の順で進める。
読み取り側の対応後、新しいセッションを撮影・承認・公開した結果から新しいdataset版を作成する。セッションを横断するsplit・クラスID・学習runの台帳保存先は学習側で別途設計する。従来の`train`は成功済みの直近runの`best.pt`を既定の初期重みに使い、親runと重みhashを記録する。初期重みから学び直す場合は`--weights`で指定する。
新クラス追加時には出力ヘッドの調整が必要になるため、ロード時のUltralyticsログとクラス対応を確認する。

exportは現在のSQLと一致する承認済み画像だけを出力する。累積バッチなら最新のmanifestだけを入力する。
相互に重複しないバッチを合成する場合だけ、`--manifest` を複数回指定する。
同じ画像の旧版と新版を同時に混ぜることは認めない。

初期導入では、単体・複数・遮蔽を含む少数画像で、候補の再現率、UID対応精度、1枚あたり修正時間を測定する。
単一プロンプトで取りこぼす対象は、まず人手で補完する。追加推論方式への変更は別途判断する。

## テスト

各プロジェクトでは `uv run pytest`。GPU依存の環境同期を避けた検証は、ワークスペースルートで次を実行する。

```powershell
uv run --no-project --python 3.12 --with pytest --with numpy --with scipy --with pillow python -m pytest --rootdir . sam3_project/tests yolo_train/tests --override-ini "pythonpath=sam3_project/src yolo_train/src" -q
```

SQLite取り込み、幾何対応付け、キャッシュ再利用、手修正保持、承認失効、クラスID・分割固定、および模擬モデルによる横断テストを含む。
実SAM3/YOLOモデルの精度・GPU動作は、ローカル重みと対象環境で別途確認する。

## 運用上の制約

- 1つの作業領域・レジストリに対する書き込みは単一プロセスで行う。分散ジョブ・同時書き込みは対象外。
- SQLiteのトランザクションはセッション単位で、全セッションの同時点スナップショットではない。
- 承認情報はハッシュによる整合性確認であり電子署名ではない。承認バッチへの書き込み権限を制限する。
- 同一配置を別セッションへ複製した場合、完全一致画像以外の類似画像は自動検出しない。撮影運用でも評価データの独立性を保つ。
