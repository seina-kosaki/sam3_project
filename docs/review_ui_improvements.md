# YOLO・DINOレビューUI改善仕様

状態: ユーザー合意済み（2026-11-04）。仕様のみ作成、未実装。公開済み変更版と性能基準は後述の確認が必要。

## 目的・範囲

YOLOの手描き視認性、確認済み画像だけの部分公開と後日の追加公開、DINO全候補不採用の一操作保存、保存後遷移の速度を改善する。YOLO確認・公開とDINO採否・承認の独立を維持する。

既存の[撮影・レビュー手順](capture_workflow.md)、[DINO保存仕様](dino_mask_save_fix.md)、[DINO公開契約](contracts/dino_mask_publication.md)を基礎とする。YOLO公開の変更は[公開契約](contracts/yolo_publication.md)を参照。

## 入出力

- 入力: 選択セッション、現行画像・レビュー版、背景画像、撮影タグ、既存／今回描画bbox、YOLO確認状態、担当者、DINO全候補の採否・対応、既存の承認・公開情報。
- 出力: 表示用bboxとタグ一覧、保存したYOLO注釈・確認状態、公開対象／未確認件数、対象画像だけの公開成果物と台帳、DINO採否・承認・正式mask参照、保存状態／エラー、処理区間別と全体の前後時間。
- 既存の`GET /api/items`、`POST /api/reviewed`、`POST /api/annotation`、`POST /api/publish`、`POST /api/complete-review`を調整する範囲を想定する。新API・DB列・スキーマ版は本仕様では決定しない。

## 動作・制約

### 1. YOLO描画モード

- 背景画像とタグ一覧を表示し、既存bboxを非表示にする。今回新しく描画している／描画したbboxは表示し、線を黄色＋濃色の縁取りにする。
- モード切替は表示だけの変更とし、既存bbox・対応を削除しない。描画結果の保存時に既存の置換ルールを適用する。
- 既存ルールである対象タグへの対応、置換の明示確認、旧採用矩形の比較用候補への退避、1タグ・1bbox、手描きbboxをDINO候補にしない扱いを維持する。

### 2. YOLO確認と部分公開

- 「一覧確認済み」（現行表示の「一覧確認済」を含む）を「YOLO確認済み」に統一する。詳細画面でもYOLOの確認であることを明確にする。
- 選択セッションの全画像確認を必須にせず、現行のYOLO確認済み画像だけを一括公開する。未確認画像は除外する。
- 実行前に「公開対象○件／未確認○件」を表示する。公開対象は今回実際に公開する画像の件数とし、同一データの公開済み分を再登録対象に数えない。対象0件では公開できない。
- bbox・ラベル・タグ対応などYOLO注釈を編集した場合は確認済みを解除し、再確認を要求する。残存する承認や旧公開情報だけで確認済みに戻さない。
- 担当者、現行性、矩形・タグ対応の整合、空注釈の明示確認、必要な例外理由など既存の公開検証は維持する。DINO採否・承認をYOLO確認済みの根拠にしない。

### 3. 部分公開後の追加公開

- 未確認で残した画像は、後日YOLO確認後に同じセッションから追加公開できる。同一の公開済みデータを重複登録しない。この追加公開・重複防止もユーザー合意済み。
- 同一画像・同一レビュー版・同一注釈内容など、同一データの再実行を重複として扱う。画像IDだけで変更版まで同一とみなさない。実装上の照合キーは既存の画像識別、レビュー版、注釈hash、承認参照を踏まえて整理する。
- 現行は`exports/<session_id>`が既存なら拒否するため、その拒否だけを外して既存出力を上書きする変更では要件を満たさない。公開対象の絞り込みは承認処理だけでなくexportにも適用する。
- 既存出力・承認・監査履歴を勝手に削除／上書きしない。追加分の公開先、manifestの累積／差分方式、公開済み変更版の扱いは未決。新しい運用や破壊的変更は別途合意前に導入しない。

### 4. DINO全候補不採用で保存して次へ

- 「保存して次へ」の左に「すべて不採用で保存して次へ」を追加する。
- 一操作で対象画像の全候補を`rejected`として保存し、既存の採用も解除する。この明示操作では全候補の個別選択・個別mask閲覧を必須にしない。
- 通常の「保存して次へ」の個別確認条件は緩和しない。担当者・現行性・全候補indexの整合など保存検証を維持し、既存のDINO専用保存経路を使う。
- 採用PNGを新規保存しない。対象画像が所有する不要maskだけを既存のDINO保存仕様・公開契約に従って整理し、全候補不採用のDINO公開対象は0件とする。
- 保存成功後だけ既存順序の次画像へ進む。保存失敗時は現在画像に留まり、エラーを表示し、既存ファイル・確定採否・承認・公開参照を維持／復元する。
- YOLO確認済み状態、矩形、承認、公開状態を変更しない。採否履歴・推論原本を削除せず、所有不明maskを推測で整理しない。クラッシュ原子性の追加保証はない。

### 5. 保存後遷移の高速化

- 保存API、一覧再取得、次画像読み込みを分けて計測し、保存操作開始から次画像表示までの全体時間も記録する。前後で同じ区間定義を使う。
- 計測で原因を特定し、不要な全件再取得や重複処理を減らす。ただし現行性・候補整合・所有境界・上書き同意など安全検証を省略しない。
- 保存中の状態を表示し、二重送信を防止する。保存確定前に次画像へ進まない。
- 保存API成功後の一覧／次画像読み込み失敗は、保存失敗と区別して表示し、確定済み保存を未保存と誤認して再送しない。
- 同じ環境・データで改善前後を比較して報告する。絶対秒数や改善率は未合意であり、推測した閾値を受け入れ条件にしない。

## 実装時の主な責務・静的確認事項

パスは`src/sam3_pipeline/`基準。新クラスの導入は指定しない。

| 対象 | 責務・現行との差 |
|---|---|
| `interface/review.html`、`tag_review.js` | 描画の表示分離、確認名称・件数、全不採用ボタン、保存状態と計測。現行DINO保存成功後の`current.reviewed = true`など、YOLO確認への波及をなくす |
| `infrastructure/review_server.py` | `_publish`の全画像確認要求・既存公開先拒否を見直す。確認対象・公開対象をサーバーでも限定。注釈保存時の確認解除を維持 |
| `infrastructure/annotation_store.py` | 承認・export対象の整合、追加公開の重複防止。現行exportはセッションの全承認を走査し、同一画像の複数版を拒否するため、UIだけの変更では不足 |
| `infrastructure/object_review_store.py`、`approved_masks.py` | 全不採用・mask整理・採否／承認の一体保存と失敗時復元 |
| `infrastructure/handoff_store.py` | 既存の公開条件とYOLO／DINO独立性を維持 |
| `tests/test_review_ui.py`、`test_session_outputs.py`、`test_capture_workflow.py` | 実装工程で下記条件のUI・保存・公開回帰を検証する候補 |

## 受け入れ条件

| 操作・状況 | 期待結果 |
|---|---|
| YOLO描画モードへ切替・ドラッグ | 既存bboxが見えず、新規線は黄色＋濃色縁取りで見える。切替だけでは保存済みbboxを失わない |
| 未確認画像が残るセッションで公開 | 対象／未確認件数が事前表示され、YOLO確認済みだけ公開。対象0件は禁止 |
| 部分公開後、残りを後日確認して公開／同じデータで再実行 | 追加公開でき、同一データの重複登録なし。既存公開データを損なわない |
| YOLO注釈を編集 | 確認済み解除、再確認が必要。DINO操作だけではYOLO確認済みにならない |
| 未閲覧候補・既存採用を含む画像で全不採用ボタン | 個別選択・閲覧なしに全候補不採用を一操作保存。採用PNG新規保存なし、不要mask整理後に次画像へ |
| 保存失敗／SQL確定失敗 | 次へ遷移せずエラー表示。既存データを維持／復元 |
| DINO保存前後 | YOLO確認・矩形・承認・公開状態が不変 |
| 保存中・遷移計測 | 保存中表示、二重送信なし、確定前遷移なし。同環境・同データの全体／区間別前後時間を報告 |

## 実装前に解決する質問

1. **公開済み変更版**: 同一画像の注釈変更／タグ版変更後の再公開をどう扱うか。現行は変更後の再承認が必要、同一画像の複数版の同時exportは拒否、旧出力は上書きしない。旧承認の取消・失効と既存manifest／下流の読取対象を含めて確認する。既存出力の自動置換・自動取消は未合意。
2. **追加公開の出力契約**: 累積manifestの新しい公開版か、重複しない追加バッチか。既存の`exports/<session_id>`と下流のmanifest選択をどう両立させるか。重複防止の照合単位とともに確定する。追加公開そのものを再承認待ちにはしない。
3. **性能基準**: 比較用環境・データ・計測回数・キャッシュ条件と、前後結果を基にした許容時間／改善率を合意する。現時点では時間報告までが確定条件で、速度の数値判定は未確定。
